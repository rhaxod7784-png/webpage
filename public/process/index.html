01 / 발견

시작은 대부분 아주 개인적인 질문

‘내 글의 색깔을 보고 싶다.’ ‘공연장의 생각을 짧게 남기면 어떨까?’ ‘성심당에서 빵을 산 다음에는 어디로 갈까?’ 궁금했던 경험에서 시작해 다른 사람에게도 의미가 있는지 가설을 세웁니다.

02 / 줄이기

더 많이 만들기보다 먼저 무엇을 뺄까

대전 MVP에서 로그인과 플래너를 제외했고, 텐텐텐에서는 음악 편집 기능을 줄였습니다. 처음 검증할 경험을 흐리는 기능은 다음으로 미룹니다. 어떤 선택을 버렸는지도 기록합니다.

03 / 기술 이해

AI가 구현한 코드를 다시 읽는 이유

AI 에이전트의 도움을 받지만, 그것만으로 기술을 이해했다고 생각하지 않습니다. 화면에서 API, 데이터베이스로 이어지는 흐름과 예외 처리 경로를 확인하고 수정하는 방법을 공부합니다.

04 / 검증

코드가 있다와 성공했다는 다릅니다

기획, 구현, 로컬 실행, 내부 QA, 웹 배포, 실제 사용자 성과를 별도로 구분합니다. Keyboard Canvas는 이미지 출력, 대전 MVP는 거리와 GPS 예외, 사유는 긴 녹음의 실사용 조건처럼 서로 다른 검증 문제가 있습니다.

05 / 시간

루틴은 유지하되 스택은 이동합니다

하루 24시간을 4시간씩 여섯 스택으로 분할하고 작업을 배정합니다. 주간·월간 파이프라인을 운영하되 각 프로젝트에 같은 시간을 고정하지 않습니다. 개발 여건에 따라 연장하거나 다른 작업에 시간을 배분합니다.

06 / 다시 보기

미래의 내가 현재의 판단에 질문하도록

당장 확신했던 방향도 시간이 지나면 다르게 보일 수 있습니다. 보류했던 기능, 제외한 선택, 실패한 가설을 나중에 다시 검토하려 합니다. 진행률뿐 아니라 판단 자체를 다시 살펴보는 방식입니다.
